Released April 6, 2026, BisQue Ultra is a scientific AI workbench with a durable control plane for frontier image research. It gives scientists one place to inspect BisQue resources, launch model-guided tools, watch durable runs, and recover the artifacts that prove what happened.

The current app centers the run record. A React workbench, Go control plane, durable Postgres state, NATS JetStream dispatch, Python Deep Agents workers, and a replaceable OpenAI-compatible model endpoint all cooperate around the same scientific workflow.

That architecture is the point. Scientific AI becomes useful when the answer stays attached to the resource, the run, the tool events, the generated files, and the evidence trail.

## What BisQue Ultra is

BisQue Ultra is a scientific imaging workbench over BisQue data and durable autonomous runs. The user-facing application is React and Vite. The run-control spine is Go. The long-running worker runtime is Deep Agents. The data layer is an existing BisQue deployment. The model layer is intentionally replaceable through OpenAI-compatible configuration.

That separation makes the system easier to operate and easier to trust. If the frontend loads but a run stalls, the control plane, worker, NATS transport, model endpoint, or BisQue connection can be inspected independently. If a result is produced, the output does not have to be reconstructed from prose. It can stay tied to the thread, run, event stream, and artifacts that produced it.

BisQue Ultra is built for the kinds of work where a frontier lab cannot accept a detached answer:

- scientific image and volume inspection
- BisQue search, metadata loading, upload, download, annotation, tagging, dataset creation, and module execution
- deployment-configured vision workflows such as RareSpot prairie analysis and other model-backed image tools
- sandboxed code execution and scientific calculators
- paper and research-context tools
- durable run events, downloadable artifacts, and hydrated prior conversations

BisQue Ultra persists the work, dispatches workers, hydrates prior runs, and lets the model be swapped without rebuilding the product around a single vendor.

That matters for serious research because long work fails in ordinary ways: browsers refresh, workers restart, streams disconnect, model endpoints change, and users return later. BisQue Ultra is being built so those ordinary failures do not erase the scientific record.

## Scientific file and viewer support

BisQue already provides the platform foundation for scientific images, datasets, tables, metadata, annotations, and modules. BisQue Ultra builds on that foundation.

Inside the product, scientific resources can be searched, staged, loaded, downloaded, uploaded, tagged, annotated, grouped into datasets, and passed into analysis workflows. The frontend also includes scientific viewer components for direct image and volume work, with image and OME-TIFF-oriented manifests, NIfTI-style scalar-volume inspection, slices, histograms, physical spacing, channel controls, transfer presets, and voxel probing.

The important design choice is simple: every file remains a scientific object with structure, metadata, viewer state, and downstream artifacts.

## Run provenance, artifacts, and replay

Scientific AI needs a stronger memory model than chat history. A useful answer must remain connected to:

- the thread where the work was requested
- the run that executed it
- the events that explain progress and terminal state
- the worker lease and dispatch path
- the files and artifacts produced
- the figures, reports, CSVs, XML, JSON, images, and downloads generated by tools

BisQue Ultra’s updated control plane treats those objects as first-class. Postgres stores users, organizations, threads, messages, runs, run events, artifacts, idempotency keys, worker heartbeats, and leases. NATS JetStream carries durable jobs, run events, and cancellation signals. The React app hydrates artifacts from past runs and recovers stream state after refreshes.

That is the difference between a compelling demo and a scientific workbench. A demo can impress once. A workbench has to be inspectable later.

## Domain workflows

The product is designed for real scientific breadth without flattening every domain into the same prompt pattern.

The current composer exposes resource workflows for BisQue search, advanced tag-aware search, metadata loading, downloads, uploads, dataset creation, dataset updates, annotations, tags, XML inspection, deletion, and module execution. It also exposes computation and expert-workflow controls including Pro Mode, a NumPy-backed calculator, chemistry tools, sandboxed code execution, and deployment-configured vision paths such as RareSpot ecology inference.

Some tool paths depend on deployment-configured model weights or services. That is the right boundary for a research platform: the workbench can expose the control layer while operators decide which specialized assets are provisioned in a given environment.

## What teams can safely claim now

For frontier labs, the strongest claims are operational:

- BisQue Ultra connects a React scientific workbench to a Go V2 control plane.
- The product uses Postgres for durable state and NATS JetStream for production-shaped worker dispatch.
- Deep Agents workers execute long-running tool workflows through an OpenAI-compatible model contract.
- The app can use vLLM, Ollama, or another compatible server by changing endpoint configuration.
- BisQue resources remain central: search, inspect, upload, download, annotate, tag, dataset, and module workflows are product concepts, not external footnotes.
- Runs and artifacts are designed to remain recoverable after browser refresh, reconnect, and worker restart paths.

## Deployment-specific boundaries

A given deployment’s exact model, weights, GPU services, and domain checkpoints depend on operator configuration. The public site should describe the product architecture and supported workflows; deployment runbooks can make environment-specific claims.
